# تشخیص زمینهٔ حساب API والکس

مسیر REST قبلاً با موفقیت پاسخ داده است؛ اضافه‌کردن URL وب‌سوکت یا MCP به‌تنهایی مشکل احراز هویت/مجوز را حل نمی‌کند. این اصلاح فقط مسیر GET موجود را کامل می‌کند و هیچ سفارشی نمی‌فرستد.

طبق https://developers.wallex.ir/docs/spot-intro معاملهٔ حساب اعتباری به **کلید همان حساب و هدر sub-account-client-id** نیاز دارد. ادعای «هدر فقط برای کلید حساب اصلی لازم است» مبنای تغییر مسیر سفارش نشده است. کلید تنها از WALLEX_API_KEY محیطی خوانده می‌شود؛ هیچ کلیدی در .env یا گزارش نوشته نمی‌شود. WALLEX_SUB_ACCOUNT_CLIENT_ID محیطی اختیاری است؛ شناسه باید با فهرست حساب‌های فعال خوانده‌شده تطبیق کند.

فرمان:

```text
conda run --no-capture-output -n shbk python -m wallex_bot.atlas_account_discovery --package-id 183
```

این فرمان موجودیِ زمینهٔ پیش‌فرض کلید را بدون هدر و موجودی حساب فرعی را با هدر می‌خواند. اختلاف موجودی مانع routing محسوب می‌شود؛ برابری موجودی، اثبات مالکیت کلید یا مجوز Trade نیست و هرگز api_key_matches_sub_account=true تولید نمی‌شود. دو خواندن اتمیک نیستند؛ تغییر واقعی موجودی هم می‌تواند اختلاف بسازد. تاریخچهٔ پکیج پس از 401 بدون هدر، فقط یک بار با زمینهٔ حساب فرعی آزموده می‌شود. موفقیت این خواندن نیز مجوز سفارش نیست.

پاسخ کامل و SHA-256 محلی در atlas_store/operations/account_discovery حفظ می‌شود. خروجی ترمینال خلاصه است و صدها کارمزد/بازار را چاپ نمی‌کند. خطای تاریخچه نباید باعث تعویض پی‌درپی کلید یا ساخت مدرک جعلی شود. LIVE و سقف درخواستی اپراتور تغییر نکرده‌اند.

تست‌ها بر قرارداد Header و رسیدهای واقعی موجود تکیه دارند؛ هیچ موجودی، قیمت یا Fill ساختگی تولید نشده است. نبود رسید محلی باعث Skip می‌شود، نه جایگزینی داده. این تست‌ها موفقیت اتصال کلید جاری یا خریدوفروش واقعی را اثبات نمی‌کنند.
